# ADR 0012: Optional Jev entity control and an observable relay

- Status: Accepted — architecture and development inspector approved by the project owner in the implementation request.
- Scope: Architecture §1–3 and §5; tactical control, application orchestration, development UI, optional external service.

## Context

An individual bug or TDF unit can opt into Jev decisions using its own instructions and its faction commander's instructions. Existing control remains the default. The owner requested shared faction vision, a small container published to GHCR, a build-time frontend relay address, and an inspector exposing actual inputs and outputs before enabling autonomy.

Direct calls to `https://api.typesafe.ai/v1/systemone` from localhost and the game's Pages origin were rejected by CORS during the planning probe. An authenticated Node request succeeded. The browser cannot keep a shared API key private.

## Decision

The game remains a static browser application. An optional, stateless Node relay is a separate runtime deployed by the owner. No simulation code calls the network, reads the environment, or uses a clock. Existing deterministic handlers execute the selected commands.

```text
mission -> faction observation + legal actions -> action Choice
                                                   |
                      target Choice (when needed) <-+
                              |
                movement only: route -> distance Score
                              |
   fresh state <- validated game command <- typed decision

inspector: pause at each question; retain inputs, responses and command
```

- The relay is a fixed-upstream JSON endpoint. `JevKey` is supplied at runtime; the image, build and browser never contain it. Allowed browser origins, body limits, request limits, concurrency limits and timeouts bound its operation. Origin filtering is not user authentication; the current single-player deployment has no user login. Logs contain request ID, status, duration and bounded actor/faction/turn context; prompts, battlefield state and credentials are excluded.
- `VITE_JEV_RELAY_URL` is public build configuration, read at the composition root. The release workflow takes it from the `JEV_RELAY_URL` repository variable. An absent production URL leaves Jev unavailable; local development defaults to port 8080.
- Entity configuration and faction prompts live in optional mission `jev` state. Old saves without that field use the original behavior. JSON saves contain configuration, known terrain, activation progress and the last 128 selected commands, but never promises, network credentials or inspector history. Schema v27 records the optional fields with an identity migration for v26; old builds refuse newer saves instead of misplaying a partially completed external phase.
- Knowledge is built explicitly. The existing `MissionView` is not serialized: it retains full terrain and other hidden mission data. Jev gets faction-visible entities with shared capability definitions, historical enemy locations, permitted objective locations and position-only radar contacts. Unknown enemy resources, spawn timers, event logs, seeds and the other faction's knowledge are excluded. Observations retain terrain memory for nonmovement previews; movement planning separately receives the full map layout.
- Movement paths use the full current map geometry, including floors and connectors through fog, matching the terrain the player can see dimmed. Only faction-known units supply occupancy and entity destinations. Other action previews and options use the perceived map. Execution uses the real map and may refuse an option whose remembered geometry is stale or whose route encounters an unseen occupant. A refusal ends the activation instead of repeatedly probing hidden obstacles.
- Navigation follows [the approved Jev AI loop](../design/jev-ai.md): Jev chooses a named entity/objective, extraction zone, visible harvestable carcass, radar contact, historical sighting, compass direction or retreat; the game computes a one-AP route. Tile maps and exhaustive movement tile choices stay local. Entity approaches stop beside occupied footprints on the destination floor, allowing natural half-height steps but not treating a staircase's opposite end as arrival. Extraction routes end inside a reachable extraction tile, and boarding remains a separate TDF command. An explicit extraction move arriving on the last AP queues that free command in saved activation progress; the controller executes it only after movement playback, without another model request. Ordinary moves and standing in the zone do not imply withdrawal; disabling Jev cancels the queued command. Carcass arrival uses the injected harvest handler's eligibility and range. Radar and last-seen locations offer investigation routes without disclosing hidden identities or turning intel into attack targets. The observation and exhaustive destination provider registry share a typed source projection and coverage tests. Directions maximize compass progress, and retreat maximizes separation from the nearest known hostile. Unreachable destinations are omitted rather than replaced with exploration-boundary moves.
- Movement alone has a third question: a five-level Score receives full state and the proposed move, then rates distance. The game normalizes the weighted score by four and rounds the scaled terrain cost up to a legal, nonzero stopping point on that route, preserving direction/retreat intent and the one-AP cap. Confidence is diagnostic, not a movement multiplier. A failed distance request cannot execute the unscored move. The relay and browser transport validate both Choice and Score shapes.
- Every request explains the game's AP, health, turn, knowledge and objective rules. Action-type options carry their own instructions and base AP costs and whether they end the activation; overwatch costs one AP and forfeits any remaining AP. Follow-ups repeat the selected weapon/item capability and action rules without relying on prior conversational memory. The movement-distance request includes the proposed route and its weighted cost, and explains that unused one-AP movement range is lost. The inspector and automatic controller share these descriptions.
- All ordinary action families use existing rules. Every decision starts with a compact Choice built from the actor's available abilities: each weapon, each usable item, and other actions such as move or overwatch. The next Choice, when needed, contains only targets/destinations for that exact weapon or item. Weapons and immediate explosives target visible hostile entities only, including for AOE attacks; arbitrary ground fire is excluded from Jev choices. Other equipment retains its placement rules. Actions with a single concrete command skip that question. Movement presents up to 255 compact intent choices directly; larger menus retain hierarchical grouping. Large families use region/target groups with at most 32 routing choices, then detail pages with at most 32 options and 8,000 criteria characters (a single indivisible action is retained). Every candidate remains reachable. This bounds enumeration size as well as option count; these are application budgets, not an exact tokenizer. The model chooses an existing candidate, never executable code or invented coordinates.
- Capability discovery is exhaustive over the tactical entity-command registry. New commands require a candidate provider, execution ownership and instructions at compile time; equipment kinds and mech actions have equivalent coverage. Weapon and item IDs are discovered from loadout data for either faction, including optional named weapon/equipment loadouts on bug species. Shared previews provide explosive victims and healing benefits without serializing footprint tile lists.
- Movement candidates cover only one AP, using ordinary terrain-weighted reachability. After each applied action, remaining AP triggers a fresh observation and decision. `finish` is not a model option. Actors without AP or any available actions make no inference request; internal activation completion and failure fallback still keep turn progression bounded.
- The application awaits decisions sequentially outside the pure simulation. The screen gates automatic play until all scene updates and phase banners settle. Each Jev action and ordinary bug activation finishes animating before the next decision or phase transition; the inspector pause is independent of this playback gate. A bug phase with no enabled Jev bug keeps its original synchronous runner. A mixed phase leaves a saved cursor for the app: ordinary bugs run their existing species behavior; Jev bugs choose actions until finished. TDF Jev units wait until all manual TDF actors are out of AP or the player requests End Turn. End Turn records a phase-local pending flag while Jev units finish, then advances through the ordinary bug flow exactly once. Saves retain the flag and completed actors. Turrets do not count as waiting manual actors. Jev TDF units wear a persistent light-blue label and are excluded from Tab cycling and the End Turn unspent count.
- An external decision is conditional on its mission snapshot and command sequence. State changes, configuration changes, phase changes, navigation and disposal cannot apply an old response. No automatic retry hides additional requests: a failed bug decision uses existing behavior, and a failed TDF decision holds position. Inspector cancellation is distinct from failure: it spends no AP, does not count against the activation limit, and resumes with a fresh decision when unpaused. Low confidence by itself does not invalidate a legal choice.
- The inspector exists only through the existing development-tools composition flag. Opening it pauses automatic play. Evaluate and re-run send only the first question; each explicit next step sends one follow-up against the same captured state and prompts. A step selector exposes previous responses and unsent questions. Preview never executes actions; Save explicitly persists prompt/control changes. Inspector and automatic play use the same step evaluator, builder and transport, with exact request/response records and no model-generated explanations invented by the UI.
- Normal gameplay exposes a separate **Command** editor at the center of the tactical top bar. Its faction-prompt command updates TDF orders without selecting or enabling an entity, spending AP or resetting activation progress. It uses the existing mission save field and command sequence, so changing orders invalidates a pending decision. The selected TDF unit's right-hand card exposes a Jev toggle and an icon-only entity-orders flag in its header; squad rows remain a single-line overview. Edits use the existing configuration command while preserving the untouched prompt/control fields; enabling requires a configured service, and disabling remains available. Both prompt editors share one view and isolate keyboard and scroll input from the battlefield. Unit popovers mount outside the scrolling card and retain unsaved drafts across updates to that unit. Changing selection closes and clears the draft; enemy and autonomous turret cards hide the controls.

## Consequences

Simulation remains deterministic for recorded commands, but fresh Jev decisions are external inputs and are not reproducible from the game seed alone. The inspector makes model version, probabilities, request size, latency, errors and grouped requests reviewable. A relay deployment and frontend rebuild are needed when the public address is first supplied or changed.

Current tactical actors are units. Existing commandable bugs, squads and mechs expose their available actions. Passive entities and autonomous equipment retain their existing lifecycle rules; adding a new controllable ability still requires a real game command and a corresponding candidate provider. Enemy health and weapon descriptions are treated as observable in the same way as the game's unit cards. History stores last-seen positions without inventing sighting timestamps the existing vision state does not record.

The integration follows TypeSafe's live [HTTP API](https://docs.typesafe.ai/api), [Score primitive](https://docs.typesafe.ai/primitives/score), [Choice primitive](https://docs.typesafe.ai/primitives/choice) and [hierarchical classification guidance](https://docs.typesafe.ai/cookbooks/hierarchical_classification). The transport validates the documented complete probability distribution. Jev's documented 32k-token state-plus-question limit is separate from its 255-option limit: type routing and bounded detail pages avoid putting every tile/action combination in one question. Traces include each stage, its exact request, UTF-8 byte size, elapsed time, and the upstream token usage when supplied.
